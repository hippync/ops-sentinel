# Ops Sentinel — Risk register & business case (block 1)

**Purpose of this document:** before writing any orchestration code, this register maps the risks of letting an agentic system act on production infrastructure to the specific developer gap each risk represents, and the specific Ops Sentinel mechanism designed to close it. This is the foundation the rest of the business case builds on.

**Framing:** on-call engineers currently lose the first ~45 minutes of most incidents to investigation before they can even start deciding what to do. Ops Sentinel's value is compressing that investigation phase — but only if the compression itself doesn't introduce new, worse risks. This register exists to prove that trade-off is sound before a single line of orchestration code is written.

## Risk register

Rows 1–8 are the original register. **Rows 9–13 are specification with no code behind them**, marked `[spec]`; the note below the table says what enforces each and when it can land.

| # | Risk category | What could go wrong | Detection signal | Hard rule (deterministic, not LLM-judged) | Residual risk | Developer gap this closes |
|---|---|---|---|---|---|---|
| 1 | **Execution risk (blast radius)** | Fix targets more resources than intended (e.g. a pattern match instead of a specific resource ID) | Worker's proposed action references a wildcard/tag pattern instead of a single resource ID | Validator rejects any action that isn't scoped to a single, named resource ID — blank, a wildcard (`*?[]`), a tag selector, or several resources in one string. Rejection is the only disposition this rule has: a `RuleOutcome` carries `passed` plus `detail` and no approval-path channel, so "route to strict approval" was never expressible here — that is scoring's concern (row 8). Runs over the rollback action too | Two resources sharing the same ID by config error (rare, but not zero). The pattern set is also literal rather than a regex: regex metacharacters and alternation between two names are not detected, which is residual rather than a hole only because the Executor and its IAM policy both require an exact service ARN | Today, a tired on-call engineer under time pressure is the only check against a broad, unscoped fix — no consistent second check exists |
| 2 | **Data risk** | Diagnosis step surfaces or the fix proposal includes credentials, secrets, or PII pulled from logs | Proposal text matches credential-shaped strings, key patterns, or known PII formats | Validator scrubs/rejects any proposal containing raw log content matching secret or PII patterns before it's shown to a human | Novel secret formats not covered by pattern rules | Logs routinely contain sensitive fragments today; there's no automated gate before a human reads a diagnosis — this adds one |
| 3 | **Cost risk — LLM calls** | Worker loops indefinitely, burning tokens without converging (a "denial-of-wallet" pattern) | Iteration count, cumulative token spend, or elapsed wall-clock time exceeds its cap without a validated proposal | Hard caps on the Worker's iterations, its cumulative token spend, and its wall-clock duration — all enforced by the graph runtime rather than by the Worker; on any breach, fail loudly and page a human instead of continuing | Iteration count is a proxy for spend rather than spend itself: a single iteration with a large context can satisfy the cap and still exhaust the budget, which is why the token cap sits alongside it. All three caps bind one run — aggregate spend across concurrent runs is row 12 | No equivalent exists in ad hoc Copilot-style agent use — nothing currently stops a run from silently spinning |
| 4 | **Cost risk — infrastructure** | Proposed fix itself causes unbounded spend (e.g. an autoscale fix with no ceiling) | A proposed count above the ceiling, on the primary action or the rollback action. The original signal — a scale action with *no* upper bound specified — is no longer constructible: `SetDesiredCountParams.desired_count` is a required non-negative int, so the typed payload closed that case rather than the Validator | Validator rejects any `set_desired_count` above `MAX_DESIRED_COUNT`, independent of the Worker's own reasoning, and runs over the rollback action too — a rollback can itself be a scale. Max-instance-count only: a `FixProposal` carries no view of the service's *current* count, so a spend delta is not derivable from one. The bound is on the absolute target, which means a scale-*down* to a count still above the ceiling is rejected — the resulting spend is what this row is about, not the direction of travel | A legitimate spike that genuinely needs more than the ceiling allows. `desired_count: 0` is deliberately **not** covered: it is an availability harm and this row is cost, so it passes this rule and is owned by no row — the pre-mortem below records it as bounded by nothing. Not IAM-bounded ([ADR-0007](adr/0007-row-4-cannot-live-in-iam.md)): if the code checks fail, spend is bounded only by account-level limits and detection — see the pre-mortem answer below | Manual fixes today are bounded by the engineer's judgment in the moment; an automated system needs that same ceiling made explicit and enforced in code |
| 5 | **Security risk — prompt injection** | Log content or alert text contains attacker- or bug-crafted text that looks like an instruction to the Worker or Validator | Proposal or reasoning trace references an action not derivable from the actual incident data | Treat all ingested log/alert content as data, never as instructions; test this explicitly with a crafted injection case in the demo | Novel injection techniques not covered by the test suite | Almost no student or portfolio agent projects test for this — it is a known, cited failure mode industry-wide and currently untested in most agent tooling |
| 6 | **Security risk — over-privileged execution** | Executor's IAM role has broader access than its known action set requires — or the Worker, which only ever reads, can act with the Executor's credentials | Executor role includes permissions not exercised by any defined action; or the pipeline's own process can assume the Executor's role | Executor IAM role scoped to the minimum action set at deploy time — even a fully manipulated agent cannot act outside that list. The Worker runs under a separate, strictly read-only role, and the Executor's credentials are never reachable from the pipeline's process | Privilege scope must be re-reviewed if the action set grows. No Worker policy exists yet — `infra/policies/` holds only the Executor's — and credential separation is an input to [ADR-0004](adr/0004-pipeline-runtime.md), so today this half is a design commitment rather than an enforced one. The second half of the detection signal also has no automated check: `check_iam_scope.py` reads a policy template, not a trust policy or a running process | This is the strongest guarantee in the whole system, and it doesn't depend on the Validator being correct — except for row 4's ceiling, which IAM cannot express ([ADR-0007](adr/0007-row-4-cannot-live-in-iam.md)) — most ad hoc agent tooling grants broad access "just in case" |
| 7 | **Availability / cascading risk** | The fix itself triggers a new incident (e.g. a restart causing a cold-start cascade elsewhere) | No rollback plan attached to the proposal | Validator rejects any proposal with no defined rollback step | Rollback plans can be wrong or untested themselves | Manual fixes today often lack a documented rollback too — this makes the omission visible and blocking, instead of silent |
| 8 | **Trust / reputational risk** | Validator too permissive → one bad auto-approved fix kills trust in the system; too strict → engineers route around it | Approval rate and false-positive/false-negative rate over time | Explicit, documented tolerance for false-positive rate as a designed trade-off, not an accident | Any threshold is a judgment call and will need tuning | Today there's no equivalent because there's no automated system to (dis)trust — this row exists specifically because Ops Sentinel introduces this new risk, it doesn't reduce an existing one |
| 9 | **[spec] Execution risk (stale state)** | The world changes between approval and execution — someone deploys, autoscaling moves the count, another incident's fix lands — so an approved action is applied to a system it no longer describes. [ADR-0005](adr/0005-approval-surface.md)'s own design target is an approval arriving ninety minutes later, from a phone | The observed facts a proposal depends on no longer match a live read taken immediately before the call | The proposal records the specific observed state it relies on — the current task-definition revision, the current desired count — inside the hashed content, so those facts are part of what the human approved. The Executor re-reads them immediately before the call and aborts if any has changed. The *result* of that check is written to the register as part of the execution record, keyed by `proposal_hash` and never placed inside the hashed content: mutating the proposal would invalidate the `ApprovalRecord` binding the Executor verified one step earlier, which is the same reason `secrets.py` rejects rather than scrubs. An abort pages a human with the diff; it never retries and never adapts the action. The rollback action's own preconditions are re-read on the same call and recorded the same way, carrying `subject="rollback_action"` when this lands: an unchecked rollback is an unchecked path to the same Executor, which is why row 1 already runs over both | The gap between the Executor's read and its AWS call cannot be closed without a conditional-write parameter, and none is documented for `ecs:UpdateService`. Narrowed, not eliminated | The `proposal_hash` check proves a proposal is *authentic*; nothing today proves it is still *correct*. An engineer doing this by hand re-checks the console before acting |
| 10 | **[spec] Availability risk (unverified outcome)** | The API call succeeds, the incident does not resolve, and the run closes as a success because nothing looks afterwards. The pipeline's own diagram ends at the register | The triggering alarm has not returned to `OK` within an observation window after execution | Execution must not be the end of the run. A verification stage re-reads the alarm, records the outcome in the register either way, and on a still-firing alarm pages a human with the recorded rollback attached — **routed strict, never fast-pathed**, because the rubric below forbids fast-pathing a high-severity action and a fix that failed to clear a firing alarm is high severity by construction. It does **not** roll back automatically: design principle 4 admits no auto-execution path, and an automatic rollback is one — doubly so when row 7's premise is that a fix can itself cause an incident | Alarm state lags the condition it measures, so a cleared alarm is evidence rather than proof. The offered rollback is a new proposal carrying its own `proposal_hash` and its own approval, not a click bound to the original — `ApprovalRecord` binds a `FixProposal`, never an `Action` inside one. The observation window is a judgment call, **not chosen here** | An engineer who applies a fix watches whether it worked. An automated proposal has no equivalent follow-through, so "executed" is silently treated as "fixed" |
| 11 | **[spec] Trust risk (unbounded approval window)** | Nobody clicks. A run stays suspended through a live incident, neither handled by the pipeline nor visibly handed back to a human — or a stale verdict is approved long after the evidence behind it stopped being true | A suspended run passes its approval window with no `ApprovalRecord` | Every `Verdict` carries an expiry. On expiry the run terminates as `approval_expired`, writes that terminal state to the register, and escalates; a late click on an expired verdict fails rather than executing. It never auto-approves — principle 4 again. **The window length is the author's decision and is not set here** | Escalation depends on a paging path that does not live in this repo. A window short enough to bound staleness may expire during legitimate deliberation, which is row 8's trade-off wearing a new hat | A pause with no timeout is indistinguishable, from outside, from a system that dropped the incident silently |
| 12 | **[spec] Execution risk (concurrent runs)** | One underlying failure trips many alarms; each starts a run; several propose conflicting fixes to the same service. Every run honours row 3's cap individually while aggregate token spend multiplies by the number of runs | More than one live run naming the same resource in `affected_resource_ids`, or repeat alarms for one resource inside a dedupe window | Runs are deduplicated by incident identity, and a run holds an exclusive lease on every resource it targets before the Executor acts; a run that cannot take the lease routes to a human rather than proceeding. Token spend is capped in aggregate across concurrent runs, not only within one | The lease mechanism depends on the runtime [ADR-0004](adr/0004-pipeline-runtime.md) has not chosen, so it cannot be designed before that lands. Dedupe can also merge two genuinely distinct incidents that happen to share a resource | Row 3's cap bounds one Worker and nothing bounds ten. Row 1 bounds one action's scope and nothing bounds ten concurrent single-resource actions on one service — blast radius by accumulation |
| 13 | **[spec] Security risk (classification provenance)** | Triage is an LLM stage, and `severity` and `incident_type` are its output. Both are load-bearing: severity gates the fast path in scoring (row 8), and `incident_type` selects the playbook that constrains every legal action (row 5). A misclassification — or one steered by crafted log text — buys a softer approval path or a wider action set | Triage's severity is lower than the severity the alarm's own definition assigns it, or its `incident_type` is unsupported by the alarm's metadata | Severity is the **maximum** of Triage's classification and the severity assigned to the alarm by the Terraform that defines it, read from an alarm-to-severity map committed alongside the alarms: an LLM may raise severity, never lower it. Provenance is the whole point — a map that lives in infrastructure-as-code is a source Triage cannot influence. Where the alarm's metadata determines the incident type, that value wins over Triage's. A missing map entry routes **strict** rather than passing — `max(Triage, nothing)` returns Triage's own value, so a vacuous pass would make the check exactly as trustworthy as the stage it exists to constrain, which is fail-open in a system that is fail-closed everywhere | A CloudWatch alarm state-change payload carries no severity field of its own, so this rests on the map existing; an alarm created outside Terraform has none assigned and leaves Triage unchecked. "Max" is monotone only in the safe direction — it cannot catch an over-classification that routes everything to strict, which is row 8's other failure mode | Row 5 already *assumes* these fields come from alarm metadata rather than log text — [`injection.py`](../agents/src/ops_sentinel/validator/injection.py) says so in its docstring — and nothing enforces it. This turns the assumption into a check |

**The numbers these rows imply are deliberately unset**, on the same discipline row 8's false-positive tolerance already uses: the approval window (row 11), the post-execution observation window (row 10), the dedupe window (row 12), row 3's per-run token and wall-clock budgets, and row 12's aggregate token budget across concurrent runs. Each is a judgment call to be made before the first measurement, not derived from it, and `docs/sprints.md` carries a checkbox for making them.

**None of rows 9–13 has a `docs/sprints.md` checkbox yet.** The "earliest it can land" column above is a *constraint* — the sprint before which a row cannot be built — and not a commitment that it will be. `docs/sprints.md` remains the source of truth for what is planned and what is done.

## Approval-path scoring rubric

Rather than a single approve/reject signal, each proposed fix is scored on three axes to decide its approval path:

- **Severity** — how bad if the fix is wrong
- **Confidence** — how sure the Worker agent is, based on diagnostic signal strength
- **Reversibility** — whether a clean rollback exists

**Low severity + high confidence + reversible** → fast-path human approval (single click, pre-validated)
**High severity OR irreversible** → strict gate regardless of confidence — always full review, never fast-pathed

This keeps the Validator's judgment inspectable and defensible rather than a black box, and makes the "not fully restrictive" design goal a deliberate policy instead of a guess.

## Pre-mortem question (answer before writing orchestration code)

> For the specific sandbox app used in v1: if every check in this register silently failed at once, what is the worst plausible outcome — and is that outcome already bounded by IAM scoping alone (row 6), independent of whether the Validator logic works correctly?

If the answer isn't a confident yes, the IAM scope for the Executor needs to shrink before v1 starts, not after.

### Answer (2026-09-15): no — not a confident yes

Worked under [ADR-0007](adr/0007-row-4-cannot-live-in-iam.md) as revised on the same date. "Every check failed" includes the Validator, the approval gate and the Executor's re-check, so what remains is the Executor's IAM policy and the sandbox account itself.

| Worst outcome if every check fails | Bounded by IAM? | What bounds it instead |
|---|---|---|
| Scale-out with no ceiling — unbounded spend | **No.** No condition key exists for `desiredCount`, and Service Auto Scaling max capacity does not block the call | Only account-level limits and time-to-detection. **Choice of bound still open** — see below |
| Service pointed at another family's task definition, and that family's task role | **Yes**, provided [ADR-0010](adr/0010-pin-updateservice-condition-keys.md) (Proposed) holds: an `ecs:task-definition` condition keeps it on the `orders-api` family. This pins the family name, not its task role — it holds because the Executor cannot register new revisions | — |
| Rollback to a known-bad revision inside the family (chaos #1's, for one) | No | Nothing. Residual: availability of one sandbox service with no real users |
| `desiredCount` set to 0 | No | Nothing. Same residual |
| Tasks moved to other subnets, or a wider security group attached | Subnet: a condition key exists, not pinned until subnet IDs exist. Security group: no key exists | Account hygiene, once the account exists: no permissive security group to attach (a Sprint 5 item) |
| Plaintext secrets read from any task definition | No — `DescribeTaskDefinition` has no resource-level permissions, so it is granted on `*` | Bounded only if task definitions reference secrets through Secrets Manager or SSM, never plain `environment` (a Sprint 5 item) |
| A secret shown in Slack or the audit log (rows 2, 5) | Not IAM's domain | Sandbox-only credentials that can be rotated |

**In one line:** everything except spend and one service's availability can be bounded by IAM plus account hygiene, once Sprint 5's hygiene items exist. Spend cannot — outside this repo's code, its only bounds are account-level limits and how quickly someone notices.

**What the "no" shrank.** The Executor's `ecs:UpdateService` grant now carries two conditions, proposed in [ADR-0010](adr/0010-pin-updateservice-condition-keys.md): `ecs:task-definition` limited to the `orders-api` family, and `ecs:enable-execute-command` fixed to `false`. `scripts/check_iam_scope.py` fails if either is removed, widened, or has its operator changed, and a committed test covers each case. Both use `IfExists`, which is read from the AWS docs rather than observed; Sprint 5 confirms it with real denied calls.

**Why "before v1 starts" is still met.** No Executor role exists before Sprint 5 — Sprints 1–3 run a fake executor. The rule's "before v1 starts" therefore means "before the role is applied", and `docs/sprints.md` puts the spend bound ahead of applying the role.

**Still open — the author's call.** How to bound spend outside the code. Each option is either a block or a lagging correction:

- **Fargate vCPU service quota** — a block, if the quota can be set low enough. Whether a quota can be lowered without a support request is **unverified**.
- **AWS Budgets action attaching a deny policy to the Executor role** — a lagging correction. Budgets act on billing data that lags usage, and a deny stops further calls without scaling down tasks already running.
- **A separate actuator role holding `ecs:UpdateService`**, which enforces the ceiling itself — a block, but made of code, and it changes the Executor's design (an ADR-0004 input).

Removing `set_desired_count` from the action set would not help: `UpdateService` permits `desiredCount` changes whether or not an `ActionType` uses them.

**Precondition this answer assumes.** The Executor's credentials are separate from the pipeline's. If the Worker's process can act with the Executor role, row 6 bounds nothing. This is an input to [ADR-0004](adr/0004-pipeline-runtime.md).
