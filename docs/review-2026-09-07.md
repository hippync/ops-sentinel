# Ops Sentinel — Senior review (Sprint 0)

**Date:** 2026-09-07 · **Scope:** all 48 tracked files at `b902a5e` · **Reviewer stance:** adversarial

A deliberately critical read of the repo as it stands at the end of Sprint 0, written to surface
what a senior engineer would say when this is public. Findings are grouped by whether they are
*wrong now*, *will be asked about*, or *positioning*. Nothing here is blocking Sprint 1; the
ordered action list is at the bottom.

---

## 1. Verdict

The README describes an A-grade system. The repo contains a well-argued design document and about
**40 lines of executable logic**, six of which are `raise NotImplementedError("Sprint 1")` —
including every file in [`agents/src/ops_sentinel/validator/`](../agents/src/ops_sentinel/validator/),
the directory the README calls "the portfolio piece."

That gap is the main risk. Nobody penalizes a scaffold on 2026-09-07 when the plan says ship in
December. But the README is written in confident present tense about a system that doesn't exist
yet, and it is written *well* — which makes the letdown sharper when a reviewer clicks into
`blast_radius.py` and finds a docstring. As of today the repo reads as **someone who is very good
at writing about engineering**. That is an ambiguous signal, and it is the one this project can
least afford, because "produces plausible-looking output with no signal about whether it's safe to
trust" is the project's own problem statement.

The thinking underneath is genuinely senior. "A safety gate judged by an LLM is not a safety gate,"
"limits are enforced outside the thing they limit," fail-closed defaults, and the risk-row → module
→ test 1:1 traceability are better instincts than most people with five years in. The critique
below is hard because the ideas are worth defending properly, not because they are wrong.

## 2. Technology choices, interrogated

### 2.1 LangGraph — the weakest justification in the stack table

The pipeline is **five nodes, near-linear, with one capped retry loop**. That is a `match`
statement and a `while` loop. LangGraph is a real dependency in the critical path for a graph that
fits on a napkin.

The stated reason does not survive contact: *"the audit trail falls out of the graph rather than
being bolted on."* It doesn't. LangGraph checkpointers give framework state snapshots.
[`AuditRecord`](../agents/src/ops_sentinel/schemas/models.py#L122) is a domain object with
`incident`, `verdict`, `approval`, and `execution_result` — it will be constructed by hand either
way. The audit trail is bolted on in both worlds. Either drop the claim or restate it as "the graph
gives per-node state I can attach to the record," which is true and smaller.

The defensible argument that [ADR-0002](adr/0002-langgraph-orchestration.md) does not make: it is a
hiring-signal technology. That is a legitimate reason — but dressing a resume decision as an
architecture decision is what makes the ADR read as post-hoc rationalization. The honest version is
already sitting in the rationale: *"continuity with `jobs-radar-qc`."*

**Sequencing problem:** ADR-0002 is `Accepted` while
[ADR-0004](adr/0004-pipeline-runtime.md) (where the pipeline runs) is `Not yet made`. The
orchestration library was picked before the runtime. If Step Functions wins ADR-0004 there are two
orchestrators and LangGraph becomes a node body. Either decide the runtime first, or state plainly
that LangGraph is fixed and ADR-0004 is really just "Lambda vs. long-running ECS task."

**Version risk:** `langgraph>=0.2` is unbounded in
[`pyproject.toml`](../agents/pyproject.toml#L7). LangGraph 0.x ships breaking changes between
minors, and there is a hard December demo. Pin an upper bound or commit a lockfile — a broken
`pip install` in week 14 is a plausible way to lose the project.

### 2.2 Java + Spring Boot + JPA + Flyway + RDS

The README's own Why column says the quiet part: *"Covers the Java/Spring side of the job search."*
That line should come out. Not because it is dishonest, but because it is the only row in the table
justified by the author's needs rather than the system's, and a reviewer's eye snags on it — it
reframes the whole table as resume-driven.

The engineering critique: the pipeline needs a service that returns 5xx on command, leaks memory
until it OOMs, and writes a log line. That does not require Spring Data JPA, Flyway, Postgres, and
RDS. The Orders domain touches **zero** incident types — no alarm, no Validator rule, and no chaos
trigger reads the database. It is a dependency that exists to be a dependency.

Two coherent positions; pick one:

- **Keep Java, drop the data layer.** In-memory orders. Removes Flyway, JPA, Postgres, and RDS, and
  about $15/mo. Sprint 2 gets roughly a week shorter.
- **Keep all of it and own it in the README:** "the sandbox app is a second portfolio surface
  (Java 21 / Spring Boot 3 / JPA); the pipeline only needs it to fail on command." Stated
  deliberately this is fine. Discovered by the reader, it looks unexamined.

### 2.3 AWS: ECS Fargate + ALB + RDS — nobody has costed this

Rough monthly for the [planned sandbox env](../infra/terraform/envs/sandbox/README.md), running
continuously: Fargate ~$30, ALB ~$18, RDS `t4g.micro` ~$13, **NAT Gateway ~$32**. Call it
**$90–100/month** on a personal card, for a semester.

The NAT gateway is the one that stings — the largest line item, and it exists only to give
private-subnet tasks outbound internet. For a sandbox, put the Fargate tasks in public subnets with
`assignPublicIp: ENABLED` and tight security groups. Equivalent isolation in practice, ~$32/mo
saved, and it is one sentence to defend.

There is real irony in risk row 4 being "runaway infrastructure cost" while the project has no cost
ceiling of its own. Add a `terraform destroy` teardown step to the demo runbook and a short cost
note to [`infra/README.md`](../infra/README.md). A reviewer who sees the author costed their own
infra reads it as operational maturity, and it is on-thesis.

### 2.4 Choices that need no defending

Pydantic v2, Terraform for a single environment, a plain-Python validator, a no-LLM executor, and
the monorepo. All correct and all correctly argued. [ADR-0001](adr/0001-monorepo.md) and
[ADR-0003](adr/0003-no-llm-in-validator.md) are real ADRs.

## 3. Broken now

### 3.1 `proposal_hash` makes the Executor's central security check theater

[`proposal_hash`](../agents/src/ops_sentinel/schemas/models.py#L95) is a plain field on
`FixProposal`, set by whoever constructs the object — and it lives *inside* the model it supposedly
hashes. [architecture.md §3.5](architecture.md#L138) claims the Executor "re-verifies the approval
record and proposal hash before acting rather than trusting what it is handed." It is trusting what
it is handed. A compromised Worker sets `proposal_hash` to whatever matches.

**Fix:** compute it in the graph runtime over a canonical `model_dump` that excludes the field, or
make it a Pydantic `@computed_field`. This is the most concrete bug in the repo and it undermines a
trust boundary the docs explicitly claim.

### 3.2 `iterations_used` violates design principle #6

[`iterations_used`](../agents/src/ops_sentinel/schemas/models.py#L93) carries the docstring *"Set by
the graph runtime, never self-reported by the Worker."* Nothing enforces that — it is a comment, not
a control, on a field in the Worker's own output schema. "Limits are enforced outside the thing they
limit" means the count never appears in the Worker's output type at all. Keep it in graph state and
attach it to the `AuditRecord`.

### 3.3 `executor-policy.json` will be rejected by AWS

IAM policy documents do not permit arbitrary keys.
[`infra/policies/executor-policy.json`](../infra/policies/executor-policy.json) has `_comment` at
the top level, inside a statement, and — worst — as a `Condition` operator. This fails
`MalformedPolicyDocument` on apply. Move the commentary into a Terraform `jsonencode()` block (HCL
has comments) or a sidecar `.md`.

### 3.4 The IAM policy does not match the action set, so risk row 6 is weaker than claimed

The `ActionType` enum has three entries. `ecs:UpdateService` is **one** IAM action that grants all
three — plus the ability to point the service at *any task definition revision in the account*. So
"even a fully manipulated agent cannot act outside that list" is not what this policy enforces.

The `Condition` TODO — *"bound desired-count changes here, not only in the Validator"* — is likely
not achievable: IAM does not appear to expose a condition key for `UpdateService`'s `desiredCount`
parameter. **Verify this before building a sprint on it.** If confirmed, the honest resolution is
that **row 4's ceiling cannot live in IAM**; bound it with Service Auto Scaling max capacity (and
do not grant `application-autoscaling:*`), then add a caveat to the "IAM is the last line of
defense" claim naming row 4 as the exception. A reviewer who finds that gap unaided will discount
everything else; a project that names its own exception looks rigorous.

### 3.5 The CI workflow has a comment that lies about what the code does

[`.github/workflows/ci.yml`](../.github/workflows/ci.yml#L12-L16):

```yaml
# Path-filtered: a Java-only change should not run this suite (see ADR-0001).
if: |
  github.event_name == 'push' ||
  contains(join(github.event.pull_request.labels.*.name, ','), 'agents') ||
  true
```

`|| true` makes the entire condition constant. It is not path-filtered. This is the finding a senior
reviewer hits fastest, and it is disproportionately damaging because the project's whole thesis is
"don't trust claims, verify them." Use the workflow's `paths:` trigger or `dorny/paths-filter`.

### 3.6 The terraform CI job is vacuous

`terraform fmt -check -recursive` runs against [`infra/terraform/`](../infra/terraform/), which
contains **zero `.tf` files**. Green check, proves nothing. Add `terraform validate` once config
lands; until then, do not ship a badge-shaped no-op.

### 3.7 The quickstart does not run

[README.md:199](../README.md#L199) says `./mvnw spring-boot:run` — there is no `mvnw` in
[`sandbox-app/`](../sandbox-app/). Line 202's `terraform init && terraform plan` runs in a directory
with no config. `pytest` passes 2 tests that assert Pydantic's own `min_length` works. Anyone
evaluating this will paste those three blocks; two fail within 30 seconds. Either commit the Maven
wrapper and mark the rest "not yet," or trim the section to what actually works.

### 3.8 Ruff `S` will break CI on the first real test

[`pyproject.toml:33`](../agents/pyproject.toml#L33) selects bandit rules; `S101` flags bare
`assert`. The current tests dodge it by using `pytest.raises`. Sprint 1's fixture tests will not.
Add now:

```toml
[tool.ruff.lint.per-file-ignores]
"tests/**" = ["S101"]
```

### 3.9 Minor, free

- No `py.typed` marker despite `mypy strict` and hatchling wheel packaging.
- No `permissions: contents: read` on the workflow — cheap credibility on a security-flavored repo.
- No `concurrency` cancel-in-progress; no pip caching.
- No `LICENSE` on a repo intended to be public.

## 4. Design holes a reviewer will poke

### 4.1 `injection.py` is oversold

The check reduces to `action.target_resource_id in incident.affected_resource_ids`. That is a good
invariant — cheap, deterministic, and it genuinely defends something. But it is
**target-derivability, not prompt-injection defense**. An injected log line cannot force a restart
of `prod-db`; it can still steer the *action type* or *parameters* on a legitimately in-scope
resource.

This will be asked in an interview. "Here is exactly what it covers and what it doesn't" is a strong
answer; "it defends against prompt injection" is a weak one.

**The ~15-line fix that makes it materially stronger:** add a playbook table constraining
`action_type` by `incident_type` (`elevated_5xx` → rollback | restart; `oom_restart_loop` → restart
| set_desired_count). Both halves of the action are then derived from structured data, not just the
target.

### 4.2 `secrets.py` says "scrubs or rejects" — those are different systems

Scrubbing mutates the proposal, which changes its hash, which breaks the chain the Executor verifies
against. Pick one: **reject** at the gate, and scrub only in the human-facing rendering layer. Right
now the ambiguity is buried in a docstring and it is a real design fork with different security
properties.

### 4.3 `Rollback.action` is an `Action` that no rule validates

[`blast_radius`](../agents/src/ops_sentinel/validator/blast_radius.py) and
[`cost_ceiling`](../agents/src/ops_sentinel/validator/cost_ceiling.py) take a `FixProposal` and will
check `proposal.action`. The rollback action is an unchecked path to the same Executor. Run the
rules over both.

### 4.4 `Action.parameters: dict[str, object]` is an untyped bag

It flows to a boto3 call, in a system whose thesis is typed boundaries. This is precisely what
Pydantic discriminated unions are for — a typed payload per `ActionType`. Roughly 30 lines, and it
turns "typed contracts" from a claim into a demonstration.

### 4.5 Two sources of truth on day one

`MAX_DESIRED_COUNT = 4` appears in
[`cost_ceiling.py:12`](../agents/src/ops_sentinel/validator/cost_ceiling.py#L12) *and* in
[`.env.example:15`](../.env.example#L15).

### 4.6 `CHAOS_ADMIN_API_KEY` defaults to empty string

[`application.yml:27`](../sandbox-app/src/main/resources/application.yml#L27). A naive `equals`
check against `""` means a request with an empty header authenticates — classic fail-open. Assert at
startup: a blank key with `CHAOS_ENABLED=true` must refuse to boot.

### 4.7 "Internal listener only" is not a boundary by itself

Both ALB listeners hit the same target group and the same container port. Enforce `/admin/**` in the
app as well (Spring Security plus the key filter). The docs imply this; state it as defense-in-depth,
since layered enforcement is the argument the rest of the project makes.

## 5. Positioning and the README

### 5.1 Two uncited statistics

[README:21-23](../README.md#L21-L23): *"one study found 80%..."* and *"a survey of 286
organizations..."* On a portfolio README read by engineers, an uncited stat is worse than no stat —
the specificity of "286" makes the missing citation louder. Link them or cut them.

### 5.2 The 45-minute baseline is load-bearing, unsourced, and not like-for-like

It is also a **success criterion**: time-to-diagnosis "framed against the ~45-min manual baseline."
That comparison will not survive one question. The pipeline handles three known incident types in a
purpose-built sandbox, with a playbook per type. A human's 45 minutes is a novel incident in an
unfamiliar production system. Presenting these as comparable invites someone to knock over the
headline number.

**Reframe — this makes the project better, not just safer:** report time-to-validated-proposal as an
absolute measurement, then **time the author doing the same sandbox incident manually** as the
honest baseline. It is a smaller number and an unattackable one. Keep the 45 minutes as cited
industry motivation, never as the denominator.

### 5.3 Present tense for things that do not exist

"Ops Sentinel lives inside the Operate & monitor phase," "The Executor re-validates rather than
trusting the record handed to it." Add a build-status line near the top:

> *Sprint 0 of 6 — contracts and CI are in place; the Validator's rules land in Sprint 1.*

One sentence converts "overclaiming" into "transparent progress," and transparency about state is
on-brand for this specific project in a way it would not be for others.

### 5.4 Three of six ADRs are empty

[ADR-0004](adr/0004-pipeline-runtime.md), [ADR-0005](adr/0005-approval-surface.md), and
[ADR-0006](adr/0006-audit-log-store.md) are all `Status: Proposed` / `Decision: Not yet made`. Those
are GitHub issues in ADR costumes. Six-with-three-hollow reads as padding; three-real reads as
discipline. Move them to issues and write the ADR when the decision is made.

### 5.5 Two commits, both scaffold dumps, 1,593 lines

On a portfolio repo the commit history *is* part of the artifact — it is the only evidence of how the
author works, and the graph is the first thing on the page. [`sprints.md`](sprints.md) preaches
incremental delivery against a cut-line list. Commit per module from here.

## 6. Ordered actions

### 6.1 Make the Validator standalone and AWS optional from the start

The strongest recommendation in this document. The plan spends Sprints 2 and 3 — four weeks, a third
of the semester — on the Java app and AWS wiring, i.e. the "everything else [that] exists to give it
something real to reject." Sprint 3 is already flagged as the riskiest, and AWS wiring is the
classic semester-eater.

The plan half-notices this already: [`scripts/README.md`](../scripts/README.md#L12) says
`replay-alarm.sh` "decouples Sprint 4 from Sprint 3, which is the plan's riskiest dependency."
Push it all the way — build the **recorded-alarm-payload harness in Sprint 1, not Sprint 4**. Then
Sprints 0 → 1 → 4 → 5 → 6 produce a complete, demoable, fully-tested pipeline with a fake executor
and zero AWS spend, and Sprints 2/3 become an *upgrade* that makes the demo real rather than a
dependency that can sink it.

The cut-line list becomes: infrastructure is cuttable, the gate is not — which is what the project
already says it is about.

### 6.2 Fix the five things that are wrong today

`proposal_hash` self-inclusion (§3.1), `iterations_used` in the Worker's output type (§3.2),
`_comment` keys in the IAM JSON (§3.3), `|| true` in CI (§3.5), and the broken quickstart commands
(§3.7).

### 6.3 Add the build-status line; cite or cut the three statistics

Ten minutes, and it is the difference between "overclaims" and "knows exactly where it stands."

### 6.4 Implement one validator rule end to end this week

[`rollback.py`](../agents/src/ops_sentinel/validator/rollback.py) is the simplest — with its
fixtures and tests. One green rule with real assertions moves the repo from "design doc" to "in
progress," and it de-risks the Sprint 1 estimate with a real data point.

## 7. Closing

The reasoning quality here is above the level of the code, which is an unusual and fixable problem —
the reverse is much harder to fix. Ship the Validator and this becomes a strong project.
